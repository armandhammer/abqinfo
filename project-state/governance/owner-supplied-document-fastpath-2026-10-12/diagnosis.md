# Bounded intake diagnosis

Baseline: `79e9ec02` (committed local PR219 production verification/closeout). Remote main at `df38bf25`; planning-snapshot at `50e66f56`. Owner specification: `9ad86801`. The checkout was clean. The earlier closeout instruction explicitly reported an integration blocker; this separate owner-directed tooling task repairs it.

## Observed causes

- PR219's reviewed `50e66f56..eb37c1ad` diff contains 41 files, 110,666 insertions and 72 deletions for 12 added page lines. Eleven contracts each contain about 7,400 lines; before/after storage snapshots each contain about 12,950 lines. These are observations of the actual diff, not estimates from the specification.
- `LeadCoalHistoricalPublication.refresh()` always invokes `audit(paths)`, saves the registry and exclusively creates the next contract, then rewrites the implementation/active pointer. It runs from setup, receipt/checkpoint and later completion flows. Contracts 4–16, 18, 20 and 21 differ from their predecessors only in registry hash (apart from timestamps): 16 of 20 refreshes have no resolved-rule or controlling-artifact change. Versions 2/3 reflect real authority/tool changes; 17/19 include real population/phase changes. Registry-wide freshness is working as designed; unconditional auditing of evolving receipts creates the unnecessary invalidation.
- `check_unregistered()` detects instruction-bearing text, including words such as “must” and JSON decision fields. Auditing such evidence changes the audit hash, which changes the registry hash, which invalidates a contract. Registering mutable receipts as authority or copying policy prose into them couples progress to authority. This implementation keeps detection and complete freshness intact. Stable authority plus factual mutable receipts avoids the loop; real new decisions still register and invalidate the contract.
- The lifecycle requires one active exact-delta guard. The Lead/Coal publication guard ignored stage endpoints and always diffed the live checkout from `50e66f56`. Its frozen publication allowlist lacked `postmerge-population.json`; even the already-authorized closeout failed with `Outside frozen scope`. A new unrelated task would also fail. Existing older guards already use `StageSnapshot`; the publication guard now follows that mechanism.
- Each bespoke task appended another stage and runner invocation. The ongoing `governed-tasks` interval instead calls the existing full `active_check('final')`: exact artifact/page/population deltas, authority, freshness, settled decisions and completion accounting. Older stages and all sealed evidence remain checked; future task populations still start from the preceding validated committed state. There is no new per-document validator or test registration.

## Result and unavoidable work

The implementation changes the existing historical publication guard and lifecycle module/tests, adds one durable procedure and an AGENTS pointer, and registers explicit scoped supersessions. It adds no intake Python module and leaves the normal validation runner and resolver unchanged. Prior AGENTS text and its original hash are retained in the supersession receipt; all other instructions retain their effect. The original 15–30-entry preference still applies outside explicitly named ordinary 1–3-document intake.

Routine work now follows freeze/resolve → focused integrity and representative review → targeted scope/quality/provenance/family assessment → exact authorized archive → owner-review PR → separately authorized narrow production closeout. Record real evidence in the existing inventory/implementation/receipt instead of regenerating wrappers. Actual authority/population changes, manual review and archive verification remain necessary. A policy/tooling change needs an initial contract and a replacement after its registered changes; elapsed time or a receipt update alone needs no replacement.

The read-only demonstration reuses the completed 122-page review and archived public-byte/preview/production receipts, checks current local originals and duplicate/entry identities, and resolves the whole current registry. Existing destination keys cause a skip/reconcile result, not another upload. Historical receipts are labeled historical; there is no fresh archive request. This task has zero R2 operations and zero visible/inventory changes relative to its implementation baseline.

Exact implementation diff totals, test results and integration observations are recorded in `receipt.json` and `integration.json` after verification. The prior 21 contracts and their evidence are preserved rather than rewritten to improve the apparent file count.

One existing negative regression cloned `policy-agents` assuming it remained active. Explicit supersession made the cloned fixture inactive, so the new-active-rule test ceased to test its intended condition. It now selects an active global rule. This real test-code change and its two additional frozen evidence paths required a third immutable contract; the earlier two snapshots remain preserved. This is a documented implementation correction, not receipt-driven churn.
