# Durable task governance

This is standing project policy established by the owner's September 27 governance instruction. Its ID is `policy-durable-task-governance`. The registry is the exhaustive authority index. CURRENT, memory, chat, discovery searches and filename chronology cannot substitute for it.

For every substantive document/family review, inventory disposition, quality assessment, consolidation, archival operation, content implementation/removal, placement/cross-listing change or other visitor-visible change:

1. Inspect branch/worktree and CURRENT. Preserve unrelated work.
2. Save a population JSON with `task_id`, forty-character `baseline_commit`, and explicit arrays `candidate_ids`, `families`, `pages`, `operation_classes`, `artifact_paths`. Include anticipated output paths. Freeze exact queue membership before review; do not silently add related masters. Family membership in the registry is automatically inferred from candidate IDs. Page selectors conservatively include rules for that page, even if a family label was omitted.
3. Run `python scripts/project/Resolve-TaskGovernance.py resolve --population <file> --output <new-contract-file>`. The resolver loads the entire active registry, verifies every controlling hash, includes all global rules and applicable scoped rules, and saves the complete rules, settled questions, gates and conflicts. Contracts use exclusive creation and an independently pinned hash. Never overwrite a contract.
4. Review/implement under that contract. Use `query --contract <file> --candidate <id>` to retrieve attached rules without repeated manual reading. Persist a task implementation plan and append activity events for substantive work. An event identifies operation, candidates, applicable IDs, question ID where relevant, and whether it implements, researches, decides or requests review. All settled questions must be implemented, not re-researched/re-decided/sent back for human review. Required actions need factual completion evidence; acknowledgement alone does not establish quality, provenance, archival authority or owner approval.
5. Before the first mutation, and again at each mutation entry point, run `active --phase mutation --operation <class>`. Set `project-state/governance/active-task.json` to the exact population, immutable contract/hash and implementation file. Freshness checks population, registry, complete active ID set, controlling artifacts, new instructions, scoped rules and gates. No mutation may begin with a conflict or unresolved applicable gate. A changed population/registry/artifact invalidates the contract: retain the old evidence, create a replacement contract, pin its hash, and rerun preflight.
6. Run the same resolver during the complete normal validation suite. Validation rejects omitted authority, changed populations/hashes, unregistered new binding instructions, silent supersession, ignored architecture, settled-question reopening and implementation outside the frozen scope. Direct edits do not bypass final inventory/content delta checks. Evidence/receipts must record actual work; validators cannot observe undocumented thoughts or conversations. All durable decisions and review activity must therefore be recorded.

The implementation JSON includes `population_sha256`, `respected_governance_ids`, `subjects` (machine-checkable architecture facts), intended `actions`, `events`, and factual `completion_evidence`. Review-phase architecture validation is distinct from mutation authorization. A compliant proposed master PDF is not permission to upload it. Gate receipts must reference registered explicit releasing authority; an invented receipt or an acknowledgement cannot release a gate.

## Binding artifacts and explicit supersession

New binding artifacts must be registered in the same logical change, identify their governance ID, authority, effective date, `active`/`superseded` state, deterministic scope, controlling artifacts and requirements/prohibitions. `governance_metadata` may identify the ID, but metadata alone is not registration. Existing evidence-only artifacts are catalogued by exact hash; changing their instruction-bearing text requires reclassification/registration. Research recommendations, logs, snapshots and provenance receipts are non-binding unless a specific continuing instruction is registered. Historical completion of an upload does not grant permission for another upload.

An active rule remains active until explicitly superseded. Stop before conflicting implementation and create a proposal with: existing governance ID; exact current decision; controlling evidence; new evidence; proposed replacement; consequences. Register the explicit owner's/project authority approving that proposal. Mark the old entry superseded with `superseded_by` and evidence; keep the old controlling evidence. Never delete an active entry, edit its requirement in place, or infer supersession from newer research, queue, PR or filename.
