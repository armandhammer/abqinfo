# Owner-approved additions and bounded document intake

Use the owner-approved path when the owner explicitly says to add a specific map, document or link and supplies its exact URL or file. This settles editorial inclusion for that exact resource. Requests to find, evaluate, review or decide whether to add retain ordinary selective scope/quality gates. The original owner-supplied review-only path remains bounded to 1–3 ordinary PDFs in an existing section; folder placement alone does not approve inclusion or external actions.

The October 14 [directive](proposals/routine-task-scope-budget-2026-10-14.md) is implemented here only for owner-approved additions, through the precise [scoped supersessions](governance/owner-approved-addition-workflow-2026-10-14/authority.json). The October 12 [specification](proposals/owner-supplied-document-fastpath-2026-10-12.md) otherwise remains controlling. No discovery, broad audit or validation-system optimization is introduced.

## One intake task

1. **Freeze and resolve.** Inspect Git status, current remote refs, CURRENT and the active task. Stop on another worker editing the checkout. Preserve unrelated work. Record exact original paths, SHA-256 and sizes, candidate IDs, existing family/entries and target page/section in the population and receipt. Include the actual expected output paths and operations, including background integration when authorized. Keep comparators read-only. Resolve the complete registry with `python scripts/project/Resolve-TaskGovernance.py resolve --population <population> --output <contract>`. Pin its hash in the implementation and active-task files. Use `query` for attached record rules; never choose historical authority manually. Check applicable settled exclusions/canonical-family decisions for specific conflicts. The owner-approved path replaces only general extra editorial/full-page/family review as explicitly registered; other stricter technical and item-specific authority still controls.
2. **Check the PDFs and material (review-only intake; approved additions use targeted checks above).** Use `Get-FileHash -Algorithm SHA256` and file length on unchanged originals. Use the installed PDF parser/renderer to check encryption, page-tree/read errors, dimensions, ending/truncation indicators, and text/image presence on every page; investigate empty pages, missing page-number sequences, repairs and rendering errors. `python scripts/project/extract_pdf.py <original>` extracts text/metadata without modifying inventory. Select an installed interpreter with the PDF dependencies first; on this checkout the bundled `C:/Users/ben/.cache/codex-runtimes/codex-primary-runtime/dependencies/python/python.exe` has pypdf and pypdfium2, while the default Python lacks them. Render the cover/title/date, contents or executive summary, representative substantive material and ending/appendices with the existing PDF tools. Record exact inspected page numbers, tools, findings and measured page/word counts. Automated page checks are not visual inspection. Map-only material needs visual review. Suspected corruption, poor scans, ambiguous substance/finality or a governing rule requires deeper/full-page inspection. Do not claim completeness solely from successful parsing or three thumbnails.
3. **Make one targeted assessment (review-only intake; approved additions use concise factual assessments above).** Confirm actual subject, publisher, date, status and official or verified historical provenance. Query only the named inventory/family and hash/URL duplicates; compare the actual existing section, editions, prior exclusions and material overlap. Retain complete structured scope and quality assessments, publication-quality evidence, series relationships and any short-document exception. Owner intent supports focus, not automatic admission. Preserve drafts/proposals as such. Escalate a specific unresolved issue instead of starting general discovery. Save decisions promptly using the existing governed inventory tools (`Update-Candidate.ps1` / `Update-CandidatesBatch.py`) and their supported schema.
4. **Archive only with current exact authority.** An explicit add request invokes the exact-original standing authority above. Folder placement or a review-only request grants no upload permission. If missing, prepare the exact files, hashes, keys, sizes and bounded request. When authorized, freeze archive objects and use `scripts/upload-r2-document.ps1` with its governed preflight: current storage inventory, the 13,000,000,000-byte project ceiling, applicable 150,000,000-byte object ceiling, absent keys, no overwrites/deletions, unchanged originals. Save intent before upload and result immediately afterward. Retrieve each complete public object and verify exact size/SHA-256. An existing key on resume requires reconciliation, never a repeated PUT. Reuse provenance/originals instead of creating redundant copies.
5. **Prepare the owner-review PR.** Add only eligible archived entries under the agreed existing heading, with concise descriptions, full archive URLs and official/verified historical source links. The exact owner-approved addition population (including one map/link), or a bounded review-only 1–3-document intake, is sufficient batch size. Run normal validation (`pwsh -NoProfile -File scripts/project/Invoke-ProjectValidation.ps1`), appropriate link checks, and `git diff --check`. Verify the nonproduction changed section. Write a real UTF-8 Markdown PR body, run `Test-PullRequestDescription.ps1`, then use `gh pr create --body-file <file>`. Describe exact visible changes with direct preview links. Stop with the content PR open and unmerged for manual owner review.

## Small durable record, stable contracts

Reuse a population, immutable contract, implementation/events and one concise receipt per task, plus genuinely necessary source/archive/preview evidence. Keep originals in place; existing exact witnesses remain valid. A receipt can record hash/size/page checks, inspected pages, provenance, duplicate/family result, assessment references, archive intent/result, public verification, PR/preview and remaining gates. Avoid copying complete inventory/storage snapshots when existing durable artifacts plus exact identities suffice.

Run `Resolve-TaskGovernance.py active --phase mutation --operation <class>` immediately before each mutation entry point. Run `active --phase final` at completion. Updating ordinary evidence/events does not itself require a new contract. Keep binding authority separate from changing receipts. Register actual decisions, classify instruction-bearing historical evidence honestly, and group known policy/tool/audit changes before resolving a replacement. Do not call the old task-specific `refresh()` functions: they create a new contract unconditionally.

A changed population, registry, audit hash or controlling artifact still invalidates the contract. Preserve the old contract and create a replacement only for that real change, explaining why. Do not preallocate forty contracts or weaken freshness to meet a numeric target. A policy implementation commonly needs an initial contract and one replacement after its authorized governance changes; routine receipt updates need neither registry edits nor an audit entry unless they contain instruction-bearing text. Binding assessments still require registration. Keep factual receipts factual; do not hide decisions in them to avoid registration.

Future tasks use the existing resolver's exact delta check through the ongoing `governed-tasks` lifecycle interval. No per-document Python module, stage, runner registration or bespoke test is needed. Completed historical intervals and sealed evidence continue to be validated. Finish and validate the current task before switching the active pointer; retain its committed population, contract, implementation and evidence. A new task starts from that validated committed state. A completed contract cannot authorize new mutations.
